# 行为验收清单

这是验收要求，不是已通过报告。所有初始结果均为“未执行”。

## 三种证据不能混用
A：确定性代码/数据库/接口/浏览器自动测试。模型输出可固定，事务和并发必须使用真实 PostgreSQL。
B：真实千问与真实业务工具联调。按配置记录模型、底座版本、测试输入、工具轨迹、草稿和 DB 结果。
C：真实麦克风、扬声器、停顿和打断验收。文字回放或模拟音频事件不能替代实际听感。

每项记录：用例 ID、证据层、运行环境与版本、实际输入、实际输出、通过/失败/未执行、证据位置。
缺少 Key/网络/设备或适配能力时标记未执行或阻塞；不能作为通过计数。
不要仅断言工具“被调用”；应断言业务状态与对用户承诺是否一致。
对话允许自然措辞和合理的工具顺序变化，不以完整逐字输出相等作为主要通过标准。

## 建议的首批真实对话材料
以下为测试输入，不是产品固定话术。日期应按测试时的商家时区和种子排班生成。

1. “皮皮，三岁的金毛，想明天下午洗澡，最好找 Lisa。你们大概多少钱？”
2. “不是皮皮，是比比。日期还是刚才那个。”
3. “下午不行，改后天上午吧。”
4. “可以，不过换成上午。”
5. “先别约，我问一下要不要带什么东西。”
6. “就这个时间，确认预约。”（仅在已呈现有效摘要后）
7. “刚刚是不是已经约上了？我这里卡住了。”
8. “我要日托，不是看医生。”
9. “算了，让店员给我回电话吧。”
10. “还是上次那个人。”（测试数据不提供历史人员）

至少保留一组未用于日常 Prompt 调整的同义表达和口语变体，用于阶段验收。
不同用例记录实际运行次数与失败轨迹；不要只重跑直到某次成功后把之前失败删除。

## 交付通过标准
适用的确定性关键约束测试必须通过；真实模型和真语音有单独结果，不得用 A 替代 B/C。
出现未确认写入、重复预约、超约、跨客户泄露、伪造成功等重大问题时不标记整体已验收。
性能先记录环境、样本数和首有效响应/工具耗时/打断延迟，再根据基线制定目标，不空口保证。
固定场景通过不是零 bug 保证，报告中保留版本、环境和未覆盖边界。
