# 宠物服务实时语音 AI 前台：产品与工程边界

状态：开发规格，不是已经实现或验收的产品。初始编制日期：2026-09-19。
本文件将产品讨论收敛为执行基线；文件名和自定义工具名属于本项目设计，不表示上游已提供同名接口。

## 目标
面向美国宠物医院、宠物美容和宠物日托商家，先完成中文网页实时语音体验。
客户自然咨询并提供信息，系统查询当前商家的真实服务和排班，得到一次明确最终确认后创建限时待付款记录；本地模拟付款成功后才成为正式预约。
客户页面与商家后台读取同一条数据库预约事实；不能只生成聊天记录或模拟凭证。

完整用户故事：进入商家网页 → 中文语音交流 → 理解/补齐需求 → 查询真实空档 → 选择 → 展示并播报摘要 → 明确确认 → 原子提交 → 客户凭证和商家后台一致。

## 范围
当前支持一家商家、一只宠物、一项服务的一次预约。日托采用当日或明确场次容量，不含过夜寄养。
支持文字补充、服务与价格咨询、信息纠正、替代时间/人员、无空档解释和真实回拨请求。
支持基础商家资料、服务、排班/容量配置和预约列表/详情。
不实现电话号码接听、外部宠物管理系统对接、真实支付平台、银行卡采集、短信邮件、复杂改期取消、商家订阅和复杂权限平台。开发验收只提供明确标注的本地模拟付款事件，不代表真实收款。
已提交预约的改期取消先引导回拨；不能把正式预约当草稿直接覆盖。
英文界面和多语种扩展不作为当前完成条件。美国业务时间、币种、联系方式语义仍需正确。

## 固定技术与运行组件
页面：React + TypeScript + Vite，一个工程内包含客户和商家路由。
语音：Qwen Audio Agent + 千问实时模型，保留底座音频和轮次机制。
适配：薄 Node 适配层，封装底座扩展和会话绑定。
业务：一个 Python/FastAPI 应用，Pydantic 契约、SQLAlchemy 数据访问、PostgreSQL。
运行规模：语音网关、业务后端、数据库；页面构建为静态资源。
不同时支持多种数据库，不额外构建通用 Agent 或微服务平台。

## 模块及依赖
网页语音组件 → Qwen 客户端/适配层 → 业务 API → 预约业务 → 数据访问。
商家后台 → 同一业务 API → 同一预约业务。
预约业务不能 import 语音库，不能调用模型，不能控制播放。
工具处理器只做参数和身份校验、调用业务服务、返回结果，不复制一套业务规则。
持久化集中处理，但不为每张表建立多层无实际价值的类。

## 上游接入需首先验证
锁定 Qwen Audio Agent 的具体可用版本或提交，并核对与之对应的公开接口。
实际验证实时模型、中文连续通话、一个真实 HTTP 只读工具、可信会话身份的传递、结果回传和打断后行为。
确认是否能在关键阶段控制摘要与结果播报；不能假定“Prompt 禁止编造”等于可强制控制音频。
不臆造新的 SDK 名称或事件名。内部路径依赖集中在适配层，并注明兼容风险。
上游不支持所需行为时，报告最小兼容方案；不自动改为整套自研语音或多模型架构。

## 对话与草稿
会话开始加载当前商家真实资料、服务目录、时区、当前草稿和约束。
使用一个对话决策模型；规则检查由业务代码完成，不设意图/规划/审核多 Agent。
小规模商家资料直接载入，不先建 RAG。
Workflow 限制业务动作的前置条件，不限制用户说话顺序。
一次表达多个字段应一次批量记入草稿；用户咨询不清空已有预约状态。
保留 ASR 原文；结构化信息是可纠正的语义理解结果。关键歧义澄清，不根据上下文擅自改写关键事实。
普通字段不重复确认；涉及当前真实歧义时可以有针对性核实。最终预约确认必须有。

草稿至少包含：客户信息与选择的联系电话、宠物、需求描述、服务、日期/人员偏好、候选/选择、缺失项、版本、待确认引用、正式预约引用。
只保存真实匹配后的服务/人员 ID；“上次那个医生”无可信历史时澄清。
商家电话、来电号码、客户联系电话分开；网页场景的来电号码为空，不填模拟值。

更新规则：未提供字段保持；显式纠正覆盖；删除单独表达；同值更新不造成无效变更。
服务、时间、人员以及影响时长的资料变化，重新检查相关候选、占位和确认。
姓名/电话变化使摘要失效，但不无条件重查排班。

## 七个业务工具（本项目自定义）
| 工具 | 行为 |
|---|---|
| get_merchant_info | 返回当前绑定商家的可公开资料、服务、价格说明和规则 |
| update_booking_draft | 批量更新草稿，返回最新状态、版本、缺失字段 |
| search_availability | 查询人员时间或日托容量，仅要求查询必要资料 |
| prepare_booking | 校验选择、短时占位、生成服务端确认快照 |
| confirm_booking | 核验当前真实确认事件、版本、占位/容量并幂等创建限时待付款记录 |
| get_booking_status | 按当前会话与确认/操作标识核实实际结果 |
| request_human_callback | 保存真实回拨请求，返回可核实结果 |

模型仅提出业务参数；商家、会话、轮次和权限上下文由服务端注入和校验。
普通字段和工具结果统一契约，后端 Pydantic 模型为字段结构的主要依据。
业务错误返回明确类型：needs_input、unavailable、conflict、expired、result_unknown 等；不能统一捕获成 success。
是否展示某工具可以按状态缩减，但即使模型调用不该调用的工具，服务端也必须拒绝违规执行。

## 确认、占位与写入
确认绑定商家、会话、草稿版本、关键业务快照、占位期限和唯一标识。
用户确认来源必须能关联真实输入轮次或页面按钮事件；模型自行写 confirmed=true 不构成授权。
“可以，不过改成上午”按修改处理；摘要未充分呈现或含糊回应不得自动提交。
自然语言授权理解仍有模型误差；时序、对象和版本校验不能替代真实语义测试。
短时占位有数据库到期时间；等待客户时不得保持长事务。
医院/美容检查完整人员占用区间和缓冲；日托检查场次容量与有效占位。
事务内并发控制与幂等提交必须覆盖所有写入口，不只语音工具。
请求超时进入待核实，按稳定服务端标识查询，不先假定失败和再次创建。
重启/断线后可查询已提交记录；查询不到且旧提交仍可能在途时不能立即判定为确定失败。
客户确认后只生成不可猜测的预约参考号和限时付款占位；正式确认码仅在服务端记录本地模拟付款成功后生成，不交给模型或前端编造。付款占位过期必须释放资源和草稿绑定。客户与商家凭证从同一条持久记录读取。

## 三类差异
医院：商家审核的分流规则、就诊需求和服务资格，不做诊断。安全转介不等于普通回拨。
美容：服务、人员、体型/毛发相关字段、时长与缓冲。
日托：日期/场次、容量、入托要求和接送时间。
采用少量明确配置和分别实现的调度函数；不先创造通用规则 DSL。

## 时区与安全隔离
交流语言与商家时区分开。使用商家 IANA 时区，最终摘要显示具体当地日期和时间。
明确处理夏令时歧义、不存在的当地时刻和跨日表达；不要按开发机北京时间预约美国时段。
不同商家以及同商家不同客户之间，语音上下文、草稿、待执行工具和回传结果均隔离。
商家后台不能仅凭前端传 merchant_id 访问数据；客户凭证不可凭可猜编号读取他人信息。
对旧查询/旧连接结果进行版本和会话检查；已提交事实需要核实并送回原会话，不应被当过时查询随意丢弃。
网页侧不保存模型 Key；日志脱敏；录音采集如需开展，先取得明确授权。

## 结果通知和降级
快速工具在同一调用链回填。只有真实操作开始后才发送等待提示。
异常返回失败或待核实，不无限等待；重连后重新查询持久事实。
SSE/已有底座事件用于刷新，通知不是数据库事实来源，断线后允许重取快照。
文字补充与手动确认复用相同业务接口，不另建一套状态。
在真实模式下未配置 Key/底座不可用时明确显示不可用；不悄悄切成模拟聊天。

## 演示与上线的区别
本地验收完成只表示该开发环境、该依赖与模型配置通过了记录中的用例。
真实商用前仍需核验部署网络、商家规则、数据处理安排、权限和实际负载；不把本地演示称为全面生产就绪。
