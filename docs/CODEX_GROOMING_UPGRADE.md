## 1. 最终产品目标

保留一个商家会话、一只宠物、一项主服务加若干明确选择的附加项目。
继续使用中文实时语音，商家时间、币种、资源来自可信配置和后端。

需要逐步实现：

客户自然咨询或一次表达多个条件
→ 识别犬/猫、套餐、必要体重与附加项
→ 后端给出有依据的价格说明和排班所需时长
→ 查询真实空档
→ 客户选择候选
→ 补齐最终预约必需资料
→ prepare 重新核实服务组合与资源，短时占位并生成摘要
→ 完整呈现摘要后，由用户明确确认
→ 同一事务创建限时待付款预约，资源持续保留
→ 客户在页面模拟支付后端确定的预约金
→ 同一预约变为 confirmed，双方读取同一事实。

这不是固定问话顺序。用户已提供的字段一次记录，当前动作不需要的资料不提前强制索取。
咨询可以随时插入。报价不强制在每次查询前单独调用；查询、准备等后端入口复用同一个组合计算函数即可。

## 3. 业务数据来源与未定事项

本任务参考用户描述的商业结构：犬类洗澡/理发按体重档计价，猫类使用独立服务配置，有套餐包含项目、收费附加项和可独立预约的单项服务。
它不授权把其他网站或先前讨论中的示意金额，当作当前演示店的已确认政策。

尚未由用户确认的内容包括：完整价格表、体重档端点归属、各组合的排班时长、预约金金额及抵扣说明。

处理方式：
- 结构和计算能力先开发；自动测试可使用明确标注为 synthetic/test/demo 的固定数据，并写明预期结果。
- 测试数据只在独立测试库或明确选择的开发演示目录生效；不得静默覆盖现有演示店配置，更不能伪装成 Ma Pet Grooming 官方规则。
- 没有结构化金额的服务继续返回原 price_note 或“待确认”，不从文字里猜价格，不把未知设成 0。
- 新计价服务没有必要的商业规则时，返回缺失配置或需澄清状态，不虚构完整报价或可预约结果。
- 不实现抓取网站、RAG、税费引擎、优惠券、真实付款、退款、短信邮件发送；这些都不属于本轮。
- 预约金建议第一版只支持“可配置固定金额”。这是开发范围建议，不代表金额已经确定。百分比、分期和退款政策暂不做。

## 4. 贯穿各阶段的业务契约

### 4.1 主服务、包含项目、附加项目分清

保留 merchant_services 作为主服务目录，不把狗、猫拆成两套预约事务。
可配置犬洗澡套餐、犬理发套餐、猫美容、单独剪指甲等；这些是目录类型示例，不表示当前门店已开通。

参与收费或时长计算的项目用稳定标识关联，不仅靠中文名称比较。
保留 included_items 用于解释，但“套餐已经包含剪指甲”必须有可计算的包含关系。
收费附加项至少能表达：项目身份、展示名称、适用物种与主服务、价格语义、排班时长增量、启用状态和来源。

要求：
- 同一个附加项重复选择不重复收费、不重复增加时长。
- 已包含项目再次提出时，说明已包含，额外费用与额外时长均为 0；若是不同升级项目，必须有独立、明确的配置。
- 猫不能套犬的体重价格表；禁用、未知、跨商家、不适用于当前套餐的项目要明确拒绝。
- 独立剪指甲使用其自身主服务与人员资格，不要求客户先买洗澡套餐。
- 不提供多份附加项数量、复杂嵌套套餐、套餐继承引擎或规则 DSL。
- 数据放少量强类型 JSONB 还是小表，根据当前读取和更新路径选择一种简单方案，说明选择；不要同时实现两种存储方式。

### 4.2 金额和体重

金额使用整数最小货币单位（USD cents），或确定精度的 Decimal；不可使用二进制浮点数累计金额。
“如何计算”与“能否保证最终金额”分开：固定金额/体重档是计算方式，确定价/起价/范围/待评估是报价语义。
例如一项是起价且没有上界，合计不能伪装成有上下界的精确区间。

体重必须同时有数值和单位，保留用户声明是估计还是明确数值；这不等于商家称重核实。
首版支持明确的 lb 和 kg，转换由后端统一完成；不要由模型或前端算后直接跨档。
“35”没有单位不能默认35磅；“四五十磅”跨价格或时长档时，追问或返回待澄清，不悄悄按较低档收费。
未支持的单位应说明并澄清，不猜。

体重档必须在配置层明确端点归属。校验重叠、空档、负数、重复档、无可匹配区间；不以配置排列顺序随意选第一个。
测试可使用 [0,20)、[20,30) 等不重叠示例，但不能把这种约定声称为参考网站的真实规则。

### 4.3 报价、排班、最终预约缺失项分开

统一用计算结果表达：
- missing_for_quote
- missing_for_availability
- missing_for_booking
- 是否可预约、是否需要人工评估，以及明确原因。

体重只影响价格时，可以先查空档，随后在最终摘要前完成所需报价资料。
体重影响排班时长或服务资格时，查询前才需要补齐体重。
姓名、电话、宠物名是最终预约资料，不应无条件阻止已有服务与日期的空档查询。

附加项没有提及默认未选择，不逐项推销、不替客户全部勾选。
需要评估的项目不能只加一条提示就当作已允许预约。若商家没有安全的预留时长/预约策略，阻止该组合进入正式预约，并说明需要评估；不新增或假装存在人工回拨工具。

### 4.4 单一计算实现

新增一个小的纯业务模块，建议 service_configuration.py。
输入审核后的目录数据和明确业务条件，输出规范化组合、收费明细、报价语义、缺失项、服务/预留时长及评估状态。
模块不调用 LLM、HTTP，不控制播放，不自行开启数据库事务。

后续报价、排班、准备预约都调用同一实现，避免三套相似规则。
在事务入口先读取同一事务下可信数据，再调用纯函数，不能为了重算价格在事务中调用外部 HTTP。
价格、时长、体重档、预约金是后端派生事实，不由模型作为已决定数值写入草稿。

### 4.5 报价不修改预约

增加只读 quote_service 能力。第一版采用“显式传入询价条件”的单一接口，不悄悄与现有预约草稿合并。
可返回需要补什么信息；不要求联系人、日期或已经存在的草稿才能询价。
询价不会创建/修改草稿、占位、准备记录或预约。对比洗澡与理发价格，不改变客户已经选择的预约。

商家身份仍来自可信服务端上下文；请求不能自带金额、人员权限或其他商家身份。
允许只读报价采用 POST 承载结构化条件，但在适配层按“只读”处理，不能因为 HTTP 是 POST 就宣称可能已经下单、返回预约 result_unknown 或要求查询不存在的 operation_id。

## 5. 阶段 A —— 目录与计算，加一个只读后端报价入口

### 工作内容

1. 核对基线，运行现有能运行的检查。用简短计划列出改动文件与可能的兼容性影响，然后实施，不只返回方案。
2. 在现有服务模型及必要目录结构中增加计价/时长配置与项目关联；保留旧服务的原有字段和行为。
3. 在新配置模型使用明确校验。字段拼错不能被悄悄丢弃；不要全仓一刀切修改旧模型 extra 策略而引入无关回归。
4. 做增量迁移，并贯通配置读取→Pydantic→seed/upsert→数据库→get_merchant 的字段链。新增字段数据库读回后必须仍存在。
5. 实现 service_configuration.py 及对应纯函数测试。
6. 在 FastAPI 增加受保护的只读报价入口，复用现有身份绑定。路由名称可按项目习惯命名，例如 /api/internal/voice/service-quotes；这是建议的新入口，不是假定已存在。
7. 在独立测试目录/数据库配置犬体重档、猫独立价格、套餐包含项目、附加项和独立剪指甲的演示数据。旧演示目录无需被替换。

### 本阶段不做

不改草稿字段、生产排班路径、prepare/confirm/simulate_payment、客户支付界面。
不向实时模型开放报价工具，不修改 Qwen 补丁、VAD、播放器或续答逻辑。
后续所需草稿与快照字段先形成设计说明，不提前半接入。

### A 的完成标准

- 同一输入得到一致组合与价格；单测精确断言收费项、币种、上下界与报价语义，不只检查“返回成功”。
- 验证体重档边界、lb/kg、缺单位、估计体重、跨档不确定值、无配置/未知/禁用/跨商家项目。
- 套餐包含项目不重复收费或增加时长，重复附加项不累加，猫不走犬表。
- 报价所需体重与排班所需体重能分别表达。
- 对现有草稿执行询价前后，草稿字段/版本、准备记录、预约数量不变；无草稿也可询价且不创建草稿。
- 配置入库/读回不丢字段，重复seed不无故产生变化；新空库与已有测试库增量迁移均验证。
- 原有不使用新计价能力的服务，原 M4 行为不退化。
- 真实 PostgreSQL 未运行则明确标记未执行，不用 Mock 结果代替。

A 完成后停止，交付真实结果。不得直接继续 B/C 或把 A 称为完整新预约已完成。

## 6. 阶段 B —— 将组合贯穿草稿、排班、预约摘要和模拟预约金

仅在用户明确授权进入 B 后执行。该阶段要完成一条后端/API/客户页闭环，但暂不向语音模型开放新组合工具。

### B1. 草稿保存选择，不保存模型计算结果

增加必要的体重信息（数值、单位、是否估计）和 selected_addon_ids。字段名可以优化，但只有一份可写的权威表示。
selected_addon_ids 首版采用集合语义：未传保留，明确传空集合删除所有附加项，传入集合替换为当前明确选择；拒绝不合法值。JSON null 不冒充清空。

同步 DraftFieldName、DRAFT_MUTABLE_FIELDS、BookingDraftPatch 校验/changes、BookingDraft、SQL 模型与迁移、store 读写。组字段的 set/clear 必须一致，避免重演年龄表示相互覆盖。
新增默认空列表后，检查 start_booking_session 的“空草稿”检测；空附加项集合不应被当成已经使用过的预约会话。

版本与失效：
- 优先复用 draft.version、availability_revision、现有目录/排班版本，先写清失效矩阵，不立即增加第三套可写版本系统。
- 服务、日期、时段、人员、会改变所需时长/资格的体重或附加项变更，必须使旧候选不可用于该新条件。
- 首版允许对体重与附加项修改保守失效、重新查询，但要说明这是开发取舍，不要丢弃客户表达的首选时间。
- 姓名、电话变化仍不无条件重查排班。
- 凡改变最终展示服务、报价或预约金的实质变更，旧摘要和确认事件失效；不能在旧确认下悄悄换价。
- 犬改猫、换套餐时不继承不兼容附加项和人员资格；明确返回哪些选择需要处理，不静默保留错误组合。

### B2. 接入所有排班入口

保留 candidate_windows_for_date 核心算法；由组合计算结果提供可靠的排班时长。
必须覆盖：首次查询、替代日期、写入候选前二次占用核验、读取旧查询、prepare 的候选与完整 busy interval 复验。
不能只改第一次 search，后续又退回 service.duration_minutes。

从服务组合导出的时长加原缓冲，作为实际资源占用。人员仍需有对应服务资格；猫服务不自动分给仅支持犬的员工。
目录中影响时长/资格的配置变化纳入现有一致性机制；价格变化也必须能让未提交的旧商业摘要被识别为过期。具体采用重算比较、既有指纹扩展还是一项小指纹，选择一种清晰方案并测试，不叠加多套同步状态。

### B3. 准备、确认与历史快照

prepare 在既有事务保护中：
读取可信草稿和目录→重算组合→复验候选承载时长及资格→检查冲突→短时占位→生成摘要。

扩展现有 BookingSummary 与 summary JSONB，保存服务组合、关键体重信息、收费项及金额语义、币种、排班时长、预约金与已配置限定。摘要哈希涵盖这些关键新事实。
优先使用一个现有快照载体，不再复制几份相同价格快照。

报价后到 prepare 前变价，使用新报价并明确在摘要展示，不悄悄使用旧金额。
prepare 后、confirm 前商业条款变化，拒绝旧确认并重新准备/呈现；不能在旧摘要哈希下提交新金额。
awaiting_payment 创建后及 confirmed 后，已冻结金额和历史记录不随目录涨价变动。新的报价使用新目录，老预约读取原快照。
旧 summary 没有价格字段时兼容读取，显示“历史金额未记录”，不按今天价格回填历史，也不把 null 当免费。

confirm 的摘要完整呈现、新轮次明确同意、身份、版本和幂等门槛原样保留。
从 preparation 占位转为 awaiting_payment 占位必须在既有事务中完成，不能出现释放后再占位的空隙。

### B4. 有金额的本地模拟预约金

新组合采用服务端固定金额配置；数额及抵扣说明从明确选择的演示目录或经用户确认的配置读取，不能自行声称是真实门店政策。
金额必须是有效正数和一致币种，与已知价格范围有可解释关系；不支持的配置拒绝，不自动改成0或全款。

在准备摘要和待付款记录中固定本次应付预约金。模拟支付仅提交受保护预约凭证和幂等事件；金额以冻结的后端事实为准，不接受前端/模型改价或 paid=true 授权。
记录本次模拟支付金额、币种和方式。confirmed 表示预约成立、预约金已支付，不表示全部服务费用已结清。
保留 payment_expires_at、同一记录幂等、过期释放和网络未知结果恢复。过期后不可通过迟到的模拟支付“复活”已释放的时段。
旧版没有金额的记录需明确 legacy 展示/兼容策略，不伪造已付金额，也不暗中改变历史状态。

客户与商家 API 返回同一快照。客户页展示服务组合、价格限定、预约金、支付截止时间、付款后状态；若抵扣或余额规则未配置，显示待确认，不能自行宣称余额确定。
继续只用现有客户页、商家 API 和测试验证，不顺带建设完整商家运营后台。

### B 的完成标准

在独立真实 PostgreSQL 上验证：
1. 组合时长变长后，原本能容纳短服务的时段不可被错误保留；替代日期和旧查询读取一致。
2. 改体重/附加项使旧候选或摘要按失效规则更新，同值重试不制造新版本。
3. 同时争抢同一人员区间只有一笔有效占位；准备转待付款无空档，支付后持续占用，过期释放。
4. 报价/目录变更在正确阶段生效；旧确认不接受新条款，已提交快照不随涨价改变。
5. 模拟付款重复点击、同事件重试、确认或付款响应丢失不生成第二笔；付款与过期竞争有确定结果。
6. 模型或前端篡改金额、币种、商家或预约身份均不能越权。
7. 新旧预约读取、已有草稿恢复、第二笔新预约均不回归。
8. 页面显示、API 与数据库的价格快照/预约金/状态一致，迁移可复验。

B 完成后停止；没有金额的legacy记录和新的带金额组合不能混成一个含糊的成功说明。

## 7. 阶段 C —— 接入同一个实时语音前台并验收体验

仅在 B 已完成且用户授权后执行。

### 工具与适配

增加 quote_service 一个只读工具，复用 A 的 HTTP 能力。
需要同步 actual Session schema、环境许可集合、BUSINESS_TOOL_NAMES、运行时处理器、能力边界和针对性测试；不能只加在 Prompt 里。
原先“六工具”的精确断言可以更新为批准后的七工具集合，但不得改成无约束或重新开放通用后台工具。

新增字段贯通网关 DRAFT_FIELDS、clear_fields、工具 schema 与后端定义。机器引用可以保留，客户话术不朗读内部 ID。
报价、更新、查询、准备、状态回执只投影真实结果；未知不写成0、false或已成功。
普通询价结果不得被伪装为“当前预约已改为这个组合”。

新增的业务工具定义与字段描述优先放在自有网关模块，Qwen 补丁只做必要加载/注册。
若需要先提取现有工具定义，做成独立无行为变化提交并跑原白名单测试。不要重写兼容补丁体系。
不得把定价、体重分档、猫犬规则、金额计算或预约金判断写入 Qwen runtime。

保留现有唯一轮次控制、播放队列、受控摘要、forceContinuation、打断旧结果保护和恢复机制。
新增 quote 的错误按只读处理；它不应被通用“POST可能已提交预约”分支误导。

### 对话和摘要

使用当前商家动态时间，测试不用已过期的固定日期。
报价缺体重只问体重；查询缺日期只问日期；最终联系人缺失不阻止本来可执行的查询。
用户一句说犬、35磅、理发、刷牙、未来周六下午，应一次理解并推进，不逐字段重问。
套餐已含剪指甲时直接说明已含，不能额外收费。
附加项未提不逐个询问；咨询价格不自动选套餐、占位或提交。
用户补齐上轮所问信息后，继续原目标；复用现有更新后查询，不新增 Planner。

服务端摘要增加真正影响同意的事实：套餐/付费附加项、关键体重档、具体时间人员、报价或范围限定、应付预约金及已配置的抵扣说明。
语音可以简洁，页面展示完整明细；但不能省掉收费与付款要求等关键条款。
同步 summarySpeech 与 presentationTranscriptMatches 等受控呈现路径，验证“播报错误金额/漏掉收费附加项”不能取得有效呈现资格；也要验证常见正确数字读法可通过。
不能只改页面金额，而语音仍读旧摘要；不要为处理数字再增加一个常驻审核 Agent。

用户明确确认后进入 awaiting_payment；用户口述已付时查询原操作，不口头代付。
模拟预约金成功后说“预约已确认，预约金已支付”，不要说“全部费用已付清”。

### C 的测试场景

- 纯询价：35磅犬的洗澡与理发分别多少钱？不创建/修改草稿。
- 同一句：犬、体重、理发+刷牙、未来日期下午；只问当前真正缺失项。
- 只查时间：缺姓名电话也能查；体重只影响价格与影响时长两种配置分别测试。
- 加剪指甲：套餐已含时零增价/零增时长；独立剪指甲不要求买套餐。
- 猫：使用独立目录与有资格人员，不套犬规则。
- 修改：选好时间后增加有时长的附加项，重算并核实时段，不嘴上说“加好了”而沿用旧短区间。
- 确认：错误金额/漏项摘要不放行；正确摘要完整播放后才接受新轮次确认。
- 付款：未付不算确认；付完查询同一记录；语音、页面、商家API金额和状态一致。
- 回归：重复信息、连续改日期、打断、旧连接迟到、重启、第二笔预约及三分钟真人通话。

分层报告：确定性单测、真实PostgreSQL/API、真实模型、真人麦克风分别写。工具回执测试或文字输入不能冒充真人音频验收。

## 8. 复杂度、测试与交付要求

保持当前一套 FastAPI/PostgreSQL、一个语音网关和同一个实时模型。
不新增 Agent、规则平台、通用工作流、Redis、队列、事件总线、向量库；不大重构后端，不恢复废弃版本。
单一计算模块和少量必要的模型/迁移是允许的；不按“每张表一套多层类”设计，也不为了限定行数把所有新增业务塞进巨型文件。

阶段内按可独立回退的小提交推进，普通实现细节自行处理，不每个函数都请求确认。
只有破坏现有数据、改变权限边界或必须改变尚未确认的业务政策时才暂停该项；其他不受影响工作可继续，不能用技术猜测填补商业事实。
阶段结束时停止，不自动跨阶段。

运行已有相关测试，再补精准行为回归。不要删除断言、降低业务门槛或用Mock冒充真实链路。
记录环境问题和未执行项，不宣称“必然没有bug”。实际运行环境与锁文件不一致时明确说明。

交付简洁但可核对：
- 实际基线、完成阶段与提交；新增规则与仍未确认的商业数据。
- 修改文件及小段关键输入/输出实例，说明哪些旧能力保持。
- 真正执行的命令、结果与未执行项；数据库迁移验证。
- 核心实现、测试、配置、补丁分别统计净增删行数，不把总diff当业务代码量。
- 完整源码快照与必要运行说明，排除.env、真实密钥、依赖目录、日志、录音与数据库数据。
