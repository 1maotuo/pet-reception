## 实现事实

同一个 Qwen Realtime Session 只暴露：

1. `get_merchant_info`
2. `update_booking_draft`
3. `search_availability`
4. `prepare_booking`
5. `confirm_booking`
6. `get_booking_status`

`request_human_callback` 属于后续 M6，当前没有后端事实入口，因此未暴露且不会假成功。没有新增第二个 Agent、LangGraph、Redis、消息队列、浏览器 VAD 或第二套轮次提交逻辑。

模型参数不包含授权用的 merchant/owner/session/turn，也不能提供 presentation/confirmation event。网关用受信上下文和随机事件调用 FastAPI；后端继续执行固定商家绑定、会话隔离、版本、摘要呈现、新轮次确认、幂等事务和状态查询约束。客户 access token 与 credential URL 在送给模型前被移除，只以 `timeline.inline` 页面卡片发给发起确认的受信 WebSocket；助手不能朗读。

摘要来自服务端 `server_booking_snapshot`，由同一上游 `speak()` 队列播报。只有已开始播放、模型响应与转写完成、浏览器发送 playback-ended，且转写覆盖客户、宠物、种类、服务、员工、联系/确认语义时，网关才写入 presentation event。playback-cancelled 或用户打断不会写入；用户提前确认时受控摘要完整重播。

## B 层真实千问联调

使用项目运行中的原版 WebUI 文字入口，未路由或伪造网络响应。

输入 1：

> 你是谁？你能帮我做什么？

结果：模型自称 Paws & Bubbles 宠物美容预约前台，只说明本店服务、预约信息、空档和预约记录能力。

输入 2（一次混合意图）：

> 我叫李女士，电话是一三八零零零零五六七八，想给两岁的比熊团子预约2026年10月13日上午Lisa做基础洗护，耳朵敏感请轻柔一点。告诉我价格并查空档。

结果：真实模型保留“55 美元起、实际按犬型确认”，批量写入草稿并从 PostgreSQL 返回 Lisa 的 9:00、9:30、10:00、10:30、11:00 候选，没有逐字段重复询问。

输入 3：

> 选九点。

结果：受控入口播报完整服务端摘要，包含李女士、犬团子、基础洗护、2026-10-13 09:00、Lisa、联系电话及护理备注，并明确“现在还没有创建正式预约”。

输入 4（摘要完整结束后的新轮次）：

> 确认，就按这个提交。

结果：模型报告参考号 `BK-06F072B7F285`，状态为等待本地模拟支付，并明确支付前不算正式确认。

输入 5：

> 刚才这笔预约现在是什么状态？

结果：`get_booking_status` 返回同一参考号和 `awaiting_payment`。商家后端读取同一持久记录：客户李女士、宠物团子、基础洗护、Lisa；`confirmation_code` 为空。

B 层结果：通过上述固定流程。首次测试中在摘要音频仍播放时发送确认，后端正确拒绝 `confirmation_not_ready`；由此发现“只提示等待但不重播”的恢复缺口，现已修改为受控完整重播并加入自动回归。修复后的完整播放再确认流程通过。

## 已知边界

- 当前只支持美容演示商家；医院与日托是 M5。
- 人工回拨、取消/改约和完善的客户操作页是后续阶段，不伪装成可用工具。
- 本地模拟支付属于 M3 开发闭环；M4 语音只生成 `awaiting_payment`，不会代替客户付款或朗读凭证 URL/token。
- 真实千问文字联调属于 B 层；真人音频的声学打断延迟、噪声、慢速口音和长通话仍需 C 层记录。
