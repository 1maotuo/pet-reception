## 已实现行为

1. `booking_preparations` 保存服务端生成的摘要、摘要摘要值、候选/草稿/排班版本、呈现事件、确认事件和过期时间；活跃准备记录构成短时占位。
2. 准备接口只接受当前草稿版本和当前会话的候选 ID。服务、人员、时间、客户和宠物事实从 PostgreSQL 与受信上下文读取，不采信模型传入的商家/会话身份。
3. 确认前必须由受信协调层记录摘要已呈现；确认必须来自准备轮次之后的新 `turn_id` 和独立确认事件。确认正文采用 `extra=forbid`，`confirmed=true` 不能授权写入。
4. 任意实质草稿变更会撤销待确认准备；过期准备会清除选择并释放时段。可用性查询会排除未过期占位和已确认预约的完整 busy interval。
5. PostgreSQL 单事务创建 `bookings`、确认 preparation 并绑定 draft。稳定 `operation_id` 支持响应丢失后的状态查询；同一 preparation 重试返回原预约。
6. 客户凭证由服务端 HMAC 密钥稳定派生，数据库只保存 token 哈希。客户以确认编号加 Bearer token 读取；错误凭证统一 404。商家使用独立管理员 token 与固定商家头读取列表/详情。
7. React 客户页从 `/booking/{code}#token=...` 的 fragment 读取 token，再请求受保护 API。页面内容只来自已确认预约响应，无效凭证不显示成功结果。
